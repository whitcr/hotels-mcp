# Виправлення дефектів ШІ-чату — 10.11.2026

Виправлення підготовлені в робочій копії MCP. Коміт, push та оновлення production не виконувалися. Перевірки на сервері запускалися в окремій тимчасовій копії на `127.0.0.1:3103`, із вимкненим записом тестових повідомлень до BigQuery. Робочий сервіс на порту 3000 не змінювався.

## 1. Вартість для всіх гостей

- Нормалізація зберігає тип тарифу: цілий номер або койко-місце.
- Для койко-місць сума множиться на кількість гостей **до** перевірки бюджету та сортування. Для цілого номера множення немає.
- `totalPrice` та `pricePerNight` — суми для всіх `pricedGuests`; `unitTotalPrice` та `unitPricePerNight` — за одну одиницю. `quantity` показує кількість номерів/місць у цій пропозиції, `priceBasis` — їхній тип.
- Якщо API повернув недостатню місткість цілого номера або недостатню відому кількість місць, тариф відхиляється. Legacy API видаляє `placesAvailable` перед відповіддю; за відсутності цього поля MCP покладається на upstream-фільтр доступності за кількістю гостей, не вигадує залишок місць.
- Тарифи з невідомою одиницею, відсутньою/іншою валютою або некоректною ціною не видаються за доступні пропозиції в UAH.
- У короткий список номерів потрапляє саме тариф, від якого взята мінімальна ціна.

Контрольний приклад: «Видубичі», двоє, 31.12.2026–02.01.2027. Два місця по 480 грн коштують **960 грн**. Окремий двомісний економ-номер коштує **840 грн**; після виправлення бот коректно рекомендує цей дешевший варіант як цілий номер для двох.

## 2. Строгий фільтр хостелів

- `exclude_hostels=true` перевіряє тип об'єкта з `hotel-info`, а не тільки legacy-прапорець тарифу.
- Хостели виключаються разом із приватними номерами всередині них. Об'єкти з невідомим типом теж не проходять цей фільтр.
- Фільтр застосовується до обмеженого пулу до 200 кандидатів до фінального ліміту рекомендацій. Радіус пошуку не розширюється.

## 3. Дати та валюта

- Календарна перевірка відхиляє 31 лютого, неіснуючий місяць та 29 лютого невисокосного року.
- Обидва інструменти доступності перевіряють дати до звернення до Hotels API; минулий заїзд і виїзд не пізніше заїзду заборонені.
- Порівняння з бюджетом виконується лише для UAH. Бот не пропонує вигадану конвертацію «за поточним курсом», а просить бюджет у гривнях.
- Дати у тексті нормалізуються до `DD.MM.YYYY`; перевірені URL та параметри дат у них залишаються незмінними.

## 4. Мова та продовження діалогу

- Мова визначається з повідомлення користувача без домішок контексту сторінки готелю.
- Вибрана мова передається в кожен модельний запит і виклик інструмента, зберігається в метаданих відповіді. Короткі числові відповіді зберігають попередню мову, зокрема після перезапуску процесу.
- Для старих діалогів без мовних метаданих використовується мова попередньої відповіді.
- Додана обмежена одноразова корекція неправильної мови та внутрішніх термінів перед показом користувачеві. Вона не запускає пошук повторно.
- Для «цих вихідних» бот пропонує конкретні дати разом із питанням про бюджет. Після «Так/Да, 1000 за ніч» виконує пошук без третього підтвердження тих самих умов.

У живому повторі початковий російський діалог перейшов до пошуку Києва на 13.11.2026–15.11.2026, для двох, до 1000 UAH/ніч, у радіусі 3 км від центру. Англомовний діалог залишився англомовним після зміни Львова на Одесу.

## 5. Посилання та фактичні твердження

- Під час повторного прогону модель змінила slug одного готелю, додавши `Kiev`. Додано серверну перевірку: URL із відомим ID готелю й тим самим origin приводиться до **точного URL інструмента**. Невідомий ID або сторонній домен не авторизується.
- Контекст перевірених посилань обмежений за розміром. Для посилання на готель із попереднього повідомлення бот має повторно викликати `get_hotel_details`.
- Якщо одноразова корекція залишає неперевірені посилання або порушення перевірок представлення, така відповідь не публікується. Це захист від неправдивої відповіді, а не гарантія відсутності будь-яких майбутніх помилок моделі.
- Правила забороняють приписувати послугам оплату, безкоштовність чи включення у тариф, якщо цього прямо немає в даних конкретної послуги. У повторі сніданок описано як доступний на замовлення, без вигаданої доплати.
- Прибрано числовий «рейтинг» із нормалізації: legacy `hotel-info.rating` фактично містить `ratingConversion`, а не підтверджену оцінку гостей.
- Прибрано неправдиві обіцянки про повну відсутність зберігання повідомлень. Чат просить не надсилати персональні/платіжні дані; за запитом про зберігання має пояснювати логування з частковим маскуванням.
- Зберігаються заборони на самостійне бронювання, збір даних для бронювання, вигадані прямі контакти та рекомендації конкурентів.

## 6. Локальна черга логів

Під час повного локального тесту виявлено додаткову несумісність Windows: спроба POSIX `fsync` директорії помилково позначала успішно записаний файл як помилку. На Windows синхронізується файл перед перейменуванням; на Linux збережено також синхронізацію директорії. Тести шляхів зроблено незалежними від роздільника ОС.

## Перевірка

- Збірка TypeScript успішна.
- 37 автоматичних тестів проходять на Windows / Node 24 і Linux / Node 22.
- Усі 7 acceptance-перевірок `scripts/qa-price-date.mjs`, що раніше фіксували дефекти, тепер проходять.
- Повторено повний набір: 15 сценаріїв, 19 відповідей моделі. Додатково виконані цільові повтори після наступних виправлень, зокрема початкового діалогу, переходу року та англомовної зміни міста.
- Ціни/кількість гостей, бюджет, типи об'єктів, радіуси й походження посилань зіставлялися з результатами інструментів. Відповіді перевірялися також за змістом; HTTP 200 сам по собі не означає правильність.
- В остаточному цільовому прогоні — 6 відповідей у 3 діалогах без помилок інструментів; усі рекомендаційні URL точно збігаються з адресами інструментів. Усього перевірено доступність 38 різних посилань із повторних прогонів: усі повернули HTTP 200.
- У повному прогоні був один реальний збій upstream `fetch failed` при визначенні Києва. Бот повідомив про недоступність пошуку, не вигадав список. Окремий повтор цього сценарію завершився успішно. Мережеві збої зовнішнього API неможливо виключити зміною промпту.

Синтетичні запити, відповіді й результати інструментів збережені в [доказах перевірки](2026-11-10-chat-fixes-evidence.json), включно з проміжними невдалими випадками, які спричинили наступні виправлення.

Повторний запуск:

```bash
npm run build
node --test dist/tests/*.test.js
node scripts/qa-price-date.mjs
node scripts/evaluate-chat.mjs
```

Живий прогін використовує баланс OpenAI. Потрібні вже налаштовані `OPENAI_API_KEY` та `MCP_AUTH_TOKEN`. `CHAT_EVAL_CASES=original_weekend_ru,year_rollover` обмежує перевірку вибраними сценаріями; `CHAT_EVAL_OUTPUT` задає JSON-файл результатів. Не додавати ключі до Git. Скрипт повертає ненульовий код також за непередбаченої помилки інструмента; навмисно змодельована 503 позначена окремим сценарієм.

Попередній [звіт до виправлень](2026-11-10-chat-report.md) збережений як історична точка порівняння.

## Межі

Навантажувальний тест, реальний мікрофон телефону та повторна перевірка доставки BigQuery/GA4 у цей прогін не входили. Для нового коду не виконувався production-деплой. Програмні перевірки закривають відомі дефекти, але не доводять безпомилковість усіх можливих відповідей генеративної моделі.

Окремо: встановлення залежностей за незміненим lock-файлом повторно повідомило про 9 наявних npm-вразливостей (4 moderate, 4 high, 1 critical). Оновлення залежностей не входило до виправлення перелічених у QA-звіті поведінкових дефектів; цей ризик залишається й потребує окремої перевірки сумісності оновлень.
