# Перевірка ШІ-чату Hotels24 — 10.11.2026

Це історичний звіт **до виправлень**. Актуальні зміни й результати перевірок описані у [звіті про виправлення](2026-11-10-chat-fixes.md).

Висновок: технічні перевірки пройшли, але якість відповідей не можна вважати повністю перевіреною та коректною. Знайдено помилку ціни за койко-місце, невідповідність фільтра «без хостелів», перемикання мови та недостатню перевірку вхідних даних.

Цей прогін не змінював код або налаштування робочого сервісу. Перезапуску, коміту та деплою не було. У репозиторій додано тільки перевірки та цей звіт. Описані нижче дефекти **ще не виправлені**.

## Середовище та метод

- MCP: робочий сервіс `nodejs3000.service`, коміт `1132c91`, модель `gpt-5-mini`.
- Мобільний сайт: `https://hotels24.ua/`, мобільний User-Agent, завантажується `smart-chat.js?v=11`.
- Усі діалоги синтетичні. Переписки клієнтів не читалися; бронювання не виконувалися. Ключі й токени не включені в артефакти.
- 15 сценаріїв, 19 відповідей моделі з трасуванням викликів інструментів. Додатково один запит до реального MCP `/chat` та одна нова сесія через сайт `/smart-chat`.
- Використано розгорнутий клас `HotelChat` і справжні інструменти MCP. Це дозволило зіставити текст відповіді з аргументами пошуку та отриманими даними. Сценарій `simulated_upstream_failure` навмисно повертав помилку 503 із тестової обгортки; він не є реальною аварією API.
- Не більше двох тестових діалогів одночасно. Це функціональна перевірка, не навантажувальний тест.
- Автоматичні перевірки доповнені переглядом відповідей та джерел даних. Підхід: [офіційні рекомендації OpenAI щодо оцінювання](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

## Що працює у перевірених сценаріях

- 18 наявних тестів MCP: 18 успішних, 0 помилок, 0 пропущених.
- Тести інтерфейсу: українська, російська, англійська, регіональний код `EN_us`, резервна мова, повідомлення голосових помилок, посилання та аналітика.
- Шість сценаріїв відновлення клієнта після 409, мережевої помилки та 502: успішні. Перевірені повторне відкриття зайнятої сесії, збереження чернетки та відсутність автоматичного повторного POST.
- Тести злиття голосових транскриптів та PHP-стану/контролера: успішні.
- Реальний MCP `/chat`: 200, відповідь за 8,894 с. Без авторизації — 401; порожнє повідомлення і неправильний `previous_response_id` — 400.
- Реальний сайт: GET показує зайнятість; паралельний POST отримує 409; перший POST завершується за 8,244 с; історія містить рівно два повідомлення; сесія розблокована. Повторення того самого `message_id` повернуло попередню відповідь за 1,546 с без дублювання історії. Разом шість успішних перевірок.
- У 19 модельних відповідях не було винятків виконання. Справжні виклики інструментів не повертали помилок. Змодельовану 503 бот пояснив як тимчасову проблему без вигаданого списку готелів.
- Медіана часу відповіді моделі — 11,649 с; максимум — 35,055 с. Це час тестового виклику `HotelChat`, а не повний час завантаження сторінки.
- Усі 24 різні посилання з відповідей присутні в отриманих даних інструментів. Перевірка HEAD усіх 24 завершилася HTTP 200. Це перевіряє доступність URL, але не гарантує незмінність цін.
- Для неповного запиту бот уточнює основні умови. Для трьох ночей уточнює неоднозначний бюджет, для однієї ночі зайвого уточнення «за ніч чи за весь період» не було.
- `31 грудня — 2 січня` перетворено на `31.12.2026 — 02.01.2027`; `10–12 травня` — на `10.05.2027 — 12.05.2027`.
- На «31 лютого» та явно минулий 2020 рік бот попросив виправити дати й не запустив пошук.
- Запит біля вокзалу передав `proximity.type=railway`, радіус 3000 м. Рекомендовані об'єкти мали відстані 2700, 900 та 2400 м у даних API; бюджет і двоє гостей передані правильно.
- Для «інші варіанти» передані виключення попередніх об'єктів; повторних рекомендацій у цьому сценарії не було. Зміна Львова на Одесу спричинила нове визначення міста й пошук зі збереженими датами, гостями та бюджетом.
- Деталі конкретного готелю отримані без вимоги дат/бюджету. Перевірка його наявності використала дати та гостей без зайвої вимоги бюджету.
- За бюджету 1 грн бот не вигадав доступні готелі. На прохання забронювати не збирав контакти/платіжні дані. Не надав посилань на конкурентів і не заявив, що прямий телефон власника є на сторінці готелю.

## Підтверджені дефекти

### 1. Високий пріоритет: ціна одного місця видається за суму для двох гостей

Сценарій `year_rollover`: Київ, 31.12.2026–02.01.2027, двоє дорослих. Для «Видубичі» бот написав «загальна ціна від 480 грн» та підтвердив, що всі ціни наведені для двох.

Окремий повторний запит безпосередньо до API підтвердив:

```json
{"hotel_id":3046,"block_id":11917,"name":"Місце у загальному тримісному номері","price_type":2,"block_price":240,"min_price":{"currency":"UAH","price":480},"max_occupancy":2}
```

`price_type=2` означає ціну за місце. 480 грн — за одне місце на дві ночі; для двох потрібно 960 грн. Водночас у цьому ж готелі API повернув окремий двомісний економ-номер за 840 грн на весь період. Через неправильну нормалізацію бот також порівнює варіанти на різній ціновій основі.

Причина: `src/mappers/availability.mapper.ts` відкидає `price_type` і не враховує кількість гостей. Втрачену семантику не може надійно відновити промпт. Аналогічна проблема повторилася в результатах на травень.

Потрібно: зберігати одиницю ціни, коректно рахувати суму для всіх гостей до фільтра бюджету та сортування, явно позначати місце у спільному номері. Окремо перевірити доступну кількість місць; не трактувати `maxOccupancy` койко-місця як місткість приватного номера.

### 2. Високий пріоритет: «без хостелів» не є строгим фільтром типу об'єкта

При `exclude_hostels=true` інструмент повернув:

- біля вокзалу Львова: хостели Fortuna та «У Ельжбети»;
- перший англомовний пошук: хостел Osobnyak;
- наступні варіанти: хостели Fortuna та Leosphere.

У цих відповідях модель сама пропустила явно позначені хостели, тому рекомендації користувачеві не порушили заборону. Але гарантії на рівні інструмента немає; неправильні кандидати займають місця у ліміті результатів.

Причина підтверджується кодом legacy API: `exclude_hostel` перевіряє `price_type != 2`, тобто виключає тарифи за місце. Приватний номер у хостелі залишається. Потрібен окремий фільтр типу об'єкта в MCP, без зміни старого API.

### 3. Середній пріоритет: мова відповіді змінюється всередині діалогу

Сценарій `english_context`, третє повідомлення: `Change the city to Odesa, keep all other conditions.` Пошук правильно виконаний з `language=en`, але вся відповідь написана українською. У першому змішаному російсько-українському запиті бот також обрав українську; цей випадок менш однозначний, ніж повністю англомовний діалог.

Потрібно явно зберігати обрану мову відповіді між кроками та перевіряти її після результатів інструментів. Мова описів API не повинна перемикати мову діалогу.

### 4. Середній пріоритет: сервер приймає неможливі календарні дати

`dateSchema.safeParse()` приймає `2027-02-31`, `2027-13-01` та `2027-02-29`. Перевіряється лише форма рядка. У живому діалозі модель відхилила «31 лютого», але це не замінює перевірку сервера. Такі некоректні дати не надсилалися до production API під час перевірки.

Потрібна календарна перевірка існування дня, місяця та високосного року до виклику upstream.

### 5. Захисна перевірка: валюта тарифу не перевіряється фільтром UAH

Синтетичний тариф `200 EUR` проходить `filterAvailabilityByBudget(..., 1000, 'total')`, ніби це 200 UAH. У живих результатах іншої валюти не було, тому це підтверджений дефект захисту на тестових даних, а не встановлена помилка поточного legacy API.

Потрібно відхиляти тарифи іншої/невідомої валюти або виконувати окрему явно визначену конвертацію. У сценарії `currency` бот не шукав без бюджету UAH, але запропонував перерахунок «за поточним курсом», хоча інструмента курсів у нього немає.

### 6. Текстові та фактичні недоліки

- У відповіді `missing_fields_uk` показано технічне слово `proximity` і формат `YYYY-MM-DD`, хоча користувацький формат має бути `DD.MM.YYYY`.
- У `booking_and_contacts` бот сказав, що персональні дані «не зберігає». Це занадто широка обіцянка: повідомлення логуються з маскуванням окремих шаблонів, яке не гарантує видалення всіх персональних даних. Коректно просити не надсилати їх без заяви про повну відсутність збереження.
- У `hotel_details` сніданок описано як послугу за додаткову оплату, хоча переданий опис підтверджує тільки можливість замовити його, без явних умов оплати. Такі уточнення не можна додавати від себе.
- У сценарії з вихідними бот повторно запитав підтвердження радіуса 3 км після короткого «Да, 1000 гривен за ночь». Контекст не втрачений, але це зайвий крок, який варто перевірити окремим діалоговим регресійним тестом.

- `scripts/qa-price-date.mjs`: локальні acceptance-перевірки дат, одиниці ціни й валюти. На поточній реалізації очікувано завершуються з кодом 1; це зафіксовані невиправлені дефекти, не збій тестового середовища. Не включені до звичайного `npm test`.
- `scripts/evaluate-chat.mjs`: повторює 15 синтетичних сценаріїв через справжню модель та MCP, записує JSON для перевірки. Використовує баланс OpenAI; не запускається автоматично в CI. Відповіді потрібно оцінювати за змістом, а не лише за відсутністю винятків.

Після встановлення залежностей і складання:

```bash
npm run build
node scripts/qa-price-date.mjs
node scripts/evaluate-chat.mjs
```

Для другого скрипту в середовищі процесу мають бути `OPENAI_API_KEY` та `MCP_AUTH_TOKEN`; модель береться з `OPENAI_MODEL` (типово `gpt-5-mini`). `CHAT_EVAL_URL` типово `http://127.0.0.1:3000`; для віддаленого адресата потрібен HTTPS. Шлях результату можна задати через `CHAT_EVAL_OUTPUT`. Змінні unit-файлу systemd самі не потрапляють у звичайний SSH-сеанс. Не вставляти ключі у Git чи файл звіту.

Дати без року залишені навмисно: при повторенні потрібно оцінювати найближчу допустиму дату відносно дня нового запуску, а не очікувати завжди 2026/2027 рік. Інвентар і ціни змінюються, тому конкретні назви готелів не є незмінним еталоном.

## Межі перевірки

Це один прогін обмеженого набору сценаріїв. Він не доводить відсутність усіх помилок моделі чи таймаутів під навантаженням. Голосове введення перевірене автоматичними тестами логіки; реальний мікрофон Chrome на телефоні в цьому прогоні не тестувався. Зовнішній сервіс браузерного розпізнавання може залишатися недоступним незалежно від коду чату. Зберігання у BigQuery і звіти GA4 не перевірялися повторно.

Першочергові виправлення: ціна за місце та строгий тип об'єкта; далі календарна/валютна валідація, стабільна мова та фактична точність формулювань. Після виправлень потрібен повтор цих сценаріїв на новому коміті.
