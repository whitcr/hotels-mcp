# Журналювання ШІ-чату в BigQuery

Призначення: `map-hotels.hotels24_chat.events`, розташування датасета — `EU`.
Сервісний обліковий запис: `hotels24-chat-writer@map-hotels.iam.gserviceaccount.com`.
Роль `BigQuery Data Editor` призначається для таблиці. Доступ до виконання SQL-запитів
цьому обліковому запису для потокового запису не потрібний.

## Що записується

- `user_message`: текст отриманого повідомлення; `role=user`.
- `assistant_message`: відповідь моделі, тривалість обробки та назва моделі; `role=assistant`.
- `error`: невдала генерація відповіді; текст винятку та службові заголовки не записуються.
- `integration_test`: синтетична перевірка підключення без даних відвідувачів.

`chat_id` — випадкове значення, створене PHP-бекендом і збережене в сесії. Воно
змінюється при очищенні діалогу. `request_id` пов'язує повідомлення та відповідь
із серверними логами. Не використовуються PHP session ID, cookies чи IP-адреси.
`chat_language`: `uk`, `ru`, `en`; `chat_context`: `hotel` або `search`.
`environment`: `prod`, `stage` або `local`, визначене бекендом сайту.

Для старого бекенда без `telemetry` MCP створює окремий `chat_id` на кожний запит.
Тому для об'єднання всього діалогу потрібно викласти також зміни
`SmartChatController.php` у мобільному проєкті. Для інших клієнтів `/chat` передавайте
`telemetry.chat_id` у кожному запиті; згенерований ID також повертається у відповіді.

Перед записом на диск та відправленням маскуються звичайні адреси email, телефони,
довгі числові послідовності, Bearer-токени та деякі формати ключів. Це евристичне
маскування, а не повне знеособлення: імена, адреси та нестандартно написані контакти
можуть залишитися в тексті. Аудіо не записується. Текст обмежений 16000 символами.
Внутрішній контекст сторінки готелю не додається до повідомлення в журналі,
якщо встановлено оновлений PHP-бекенд.

Поля `input_tokens` та `output_tokens` у події `assistant_message` містять суму
`usage` усіх нових відповідей OpenAI в межах одного запиту `/chat`: початкової,
продовжень після інструментів та виправлення відповіді. Отримання старої відповіді
через `retrieve` не додається повторно. У `user_message` ці поля залишаються NULL,
щоб не дублювати витрати одного запиту. Нулі з API зберігаються як 0. Якщо хоча б
одна отримана відповідь не має відповідного показника usage, його сума — NULL.

Для події `error` зберігається відома сума вже отриманих відповідей. Якщо подальший
виклик завершився мережевою помилкою, usage цього виклику невідомий: сума в error
може бути неповною. Якщо жодна відповідь не отримана, значення залишаються NULL.
Це облік повідомлених API токенів, а не точний фінансовий білінг: кешовані вхідні
токени та інші складові можуть мати різну ціну. Вихідні токени включають також
невидимі користувачеві токени, які враховує API.

Зміна діє для нових подій після деплою MCP. Схема таблиці не змінюється, старі
рядки з NULL автоматично не заповнюються. Внутрішні виклики інструментів та результати пошуку окремими подіями
не записуються. Помилки сайту до звернення до MCP (DNS, PHP, nginx, CSRF тощо)
залишаються в логах сайту. Відхилені запити `/chat` (авторизація, валідація,
ліміт запитів, відсутній ключ OpenAI) не потрапляють у таблицю.

## Черга та доставка

Запис на диск очікується перед продовженням запиту; мережеве відправлення працює
у фоні пакетами до 100 записів кожні 5 секунд. Файли створюються з правами 0600,
каталог — 0700. Один процес MCP має використовувати один окремий каталог черги.
Каталог має бути на постійному локальному диску Linux поза репозиторієм.

Після перезапуску недоставлені записи підхоплюються з диска. За помилки повтори
відбуваються з наростанням затримки до приблизно 5 хвилин. Часткове підтвердження
BigQuery видаляє лише успішні записи. Невдалі записи залишаються для повтору;
пошкоджені файли залишаються для перевірки оператором і не блокують справні.

Ліміт черги: 64 MiB або 10000 записів; локальний строк зберігання — 7 днів.
Переповнення чи помилка диска не зупиняє чат, але новий запис тоді може бути
втрачений. Прострочені локальні записи видаляються. Такі випадки мають окремі
події журналу: `chat_log_queue_full`, `chat_log_disk_error`, `chat_log_expired`.
Потрібно відстежувати також `chat_log_delivery_failed` і `chat_log_corrupt_record`.
BigQuery має окремий строк зберігання розділів — 90 днів.

Доставка допускає дублікати після обриву з'єднання чи збою між вставленням та
видаленням файла. `insertId=event_id` дає лише найкращу можливу дедуплікацію Google,
тому для звітів прибирайте дублікати за `event_id`, як у запиті нижче.

## Локальна перевірка (WSL, Node.js 22)

Несекретні налаштування вже зберігаються у `src/logging/settings.ts`: проєкт,
датасет, таблиця, автоматичне ввімкнення, шляхи ключа та черги. Їх можна змінювати
й викладати звичайним комітом. Додаткові змінні BigQuery не обов'язкові.

Ключ автоматично підхоплюється з виключеного з Git файла `secrets/bigquery.json`
у робочому каталозі MCP або з `/etc/hotels24-chat/bigquery.json` на сервері.
Він не входить до комітів, Docker-образу чи фронтенду. Несекретні налаштування
доставляються звичайним деплоєм; ключ передається окремо один раз.
Оригінал у Downloads залишено на місці.

За замовчуванням без ключа журналювання вимкнене; з ключем — увімкнене.
Черга створюється в `~/.local/state/hotels24-chat/queue` користувача сервісу.
Під час запуску подія `chat_logging` показує `enabled: true` або `false`.
Для ADC без файла використовуйте `CHAT_LOG_ENABLED=true`. Наявні змінні оточення
мають пріоритет над налаштуваннями коду, зокрема `CHAT_LOG_ENABLED=false` вимикає запис.

```bash
npm ci --include=dev
npm run build
npm run logs:check
```

Ця команда записує одну подію `integration_test`, не звертається до OpenAI
й не надсилає реальні переписки. Успіх: `status=ok` та `event_id`.
Якщо повернуто помилку, перевірте права таблиці, увімкнення BigQuery API та білінг
проєкту. `bigquery_http_403` може означати кілька причин; сам код не доводить,
що проблема саме в ролі.

Запуск MCP із наявними параметрами чату в оточенні:

```bash
npm start
```

Якщо параметри Hotels API та OpenAI зберігаються у локальному `.env`, запускайте
`node --env-file=.env dist/src/server.js`. `.env.bigquery.local` більше не потрібний
для типового запуску, але залишається сумісним способом перевизначити параметри.
Робочий каталог має бути коренем проєкту. Для системного сервісу це вже
`/var/www/hotels_mcp`; команда `node dist/src/server.js` залишається сумісною.

## Налаштування на сервері

Ключ один раз потрібно розмістити у `/etc/hotels24-chat/bigquery.json` на MCP-сервері,
поза Git. Для поточного сервісу власник файла — root, права — 0600, каталогу — 0700.
Після цього звичайні оновлення коду не потребують повторної передачі ключа або
додаткових змінних BigQuery. Сам файл не можна додавати до коміту.

Одноразова передача з PowerShell на Windows:

```powershell
ssh -i "$env:USERPROFILE\.ssh\zal24 (2)" root@10.1.31.194 "umask 077; mkdir -p /etc/hotels24-chat"
scp -i "$env:USERPROFILE\.ssh\zal24 (2)" "C:\Important\Hotels24\hotel-mcp\secrets\bigquery.json" root@10.1.31.194:/etc/hotels24-chat/bigquery.json
ssh -i "$env:USERPROFILE\.ssh\zal24 (2)" root@10.1.31.194 "chmod 600 /etc/hotels24-chat/bigquery.json"
```

Звичайне оновлення на сервері (або ці самі дії у вашому деплой-процесі):

```bash
cd /var/www/hotels_mcp &&
git pull --ff-only origin main &&
npm ci --include=dev &&
npm run build &&
systemctl restart nodejs3000.service
```

Журналювання автоматично запускається після оновлення MCP. Для групування
повідомлень у діалоги потрібен також деплой зміненого `SmartChatController.php`
з мобільного репозиторію. Вже задані змінні оточення мають пріоритет: якщо раніше
було встановлено `CHAT_LOG_ENABLED=false`, автоматичного ввімкнення не буде.
Для вимкнення змініть `enabled` у `src/logging/settings.ts` на `"false"`, викладіть
код і перезапустіть сервіс або використайте `CHAT_LOG_ENABLED=false`.
Вимкнення не видаляє вже зібрані файли черги чи записи BigQuery.

У Docker ключ потрібно змонтувати read-only в `/app/secrets/bigquery.json`, а чергу —
на постійний том, доступний користувачу `node`. Ключ не вбудовується в образ.

Перевірка доставки: `journalctl -u nodejs3000.service --since '10 minutes ago'`.
Подія `chat_log_delivery` показує `sent`, `failed`, `pending` та безпечні коди `reasons`.

## Перегляд останніх записів

Виконуйте своїм користувачем BigQuery, з локацією запиту EU:

```sql
SELECT created_at, chat_id, request_id, environment, event_type,
       role, message, chat_language, chat_context, response_ms, error_code
FROM `map-hotels.hotels24_chat.events`
WHERE created_at >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
QUALIFY ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY created_at) = 1
ORDER BY created_at DESC
LIMIT 100;
```

Для конкретного діалогу додайте `AND chat_id = 'ідентифікатор'` до WHERE
та змініть сортування на `ORDER BY created_at ASC`. Фільтр дати обов'язковий.

## Повідомлення операторів

Роль у BQ визначається за постійним `_id` документа `crm.operators`:

- відвідувач: `role = user`;
- підтверджений оператор з `_id = 123`: `role = operator_123`;
- відповідь моделі: `role = assistant`.

Тип події оператора залишається `user_message`; схема таблиці BQ не змінюється.
У CRM `h24token` відповідає полю `token` документа оператора. Він може змінитися
після завершення строку дії, тому для аналітики використовується `_id`.

PHP мобільного та десктопного сайту читає лише cookie `h24token` і передає її MCP
у `telemetry.operator_token` через авторизований серверний запит. Поля `role`,
`operator_id` або `operator_token` з POST браузера не використовуються для
ідентифікації. MCP перевіряє кожне нове повідомлення через службовий маршрут
`GET /v1/info/crmtoken/operator?token=...` з чинним ключем Hotels API.
Успіх: `data.operator_id` — додатне ціле число (наприклад 123). Невідомий,
прострочений токен або вимкнений оператор: `data.operator_id = null`, роль `user`.
При помилці API перевірки повертається 503 `operator_verification_unavailable`:
повідомлення не надсилається моделі й не приписується іншій ролі.

Токен не записується в рядок BQ, не надсилається моделі, не повертається браузеру
та не додається до GA4. Результат перевірки не кешується між повідомленнями:
видалення/зміна cookie та відкликання доступу враховуються у наступному запиті.
Історія у браузері зберігає стандартну роль `user`, потрібну для відображення.
Ідентифікація не надає оператору нових інструментів або винятків з антиспам-лімітів.

### Порядок викладки

1. API: новий метод `getOperatorIdentityAction` у `CrmTokenController.php`,
   оновлення кешу маршрутів/OPcache за звичайною процедурою деплою API.
   Переконайтеся, що службовий ключ MCP має доступ `ROLE_SERVICE` до маршруту.
2. MCP: новий клієнт визначення ID, обробник ролі та журналювання.
3. Десктопний і мобільний сайти: оновлені `SmartChatController.php` /
   `DesktopSmartChatController.php`, що передають cookie лише сервером.

Поки новий маршрут API не викладено, не вмикайте передачу operator_token на сайтах:
старий `/info/crmtoken` повертає лише boolean і не дозволяє визначити ID.
Історичні рядки BQ не змінюються. Реального оператора можна знайти в CRM через
документ з відповідним `_id`; підміна cookie дійсним токеном іншого оператора
визначає власника цієї облікової інформації, а не фізичну особу за комп’ютером.
